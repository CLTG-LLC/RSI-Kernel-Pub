# GDPevo single-adapter pilot

Slice S4 of `docs/design.md` §7, issue #4. One campaign under the frozen pre-registration `docs/prereg-gdpevo-pilot.md`. This is a diagnostic feasibility and cost run, not the two-artifact E1a and not a statistical claim. D4 is not reported.

Status: **acceptance decided; both paired groups `updated`.** The pre-run STOP evidence, runtime pins, dev campaign, dev diagnostics, Jev comparison, adjudication, holdout, cost and exposure log below are filled from the run records. Acceptance is decided: `task_group_001` and `task_group_003` closed `updated` on the owner's approval, bound to the candidate, data and evaluator hashes; `task_group_002` closed `no_improvement` because it selected no candidate. Independent review of this report is pending (Astra, before the #4 PR).

## Diagnostic only

The pre-registration ("Uncertainty and unchanged control") fixes the scope at 3 read-only groups. With 3 groups the smallest exact two-sided paired p-value is 0.25 and the bootstrap has only 27 ordered group draws, so no significance or power claim is made. CIs are reported, not used as a gate. Passing retention is not demonstrated improvement.

### Deviation from the pre-registration

`docs/prereg-gdpevo-pilot.md:126-127` and `:141-142` require approval bound to the candidate, input, evaluator **and code** hashes. The evidence does not meet that requirement as written: `ApprovalRecord` (`src/rsi_kernel/loop.py:211`) carries only `candidate_hash`, `evaluator_hash`, `data_hash` and `approver`, so the approval record holds no code hash at all.

The full-code identity was instead enforced separately, not inside the approval: the final phase recomputes `code_hash` (over `src/rsi_kernel` plus `uv.lock`) and requires the frozen, current and recorded identities to be equal, otherwise it STOPs (`src/rsi_kernel/adapters/gdpevo/pilot.py`, `_identity_ok`). The one recorded identity change — the rebind to `docs/prereg-s4-addendum.md` — is recorded in each group's `rebind.json`. The `evaluator_hash` covers the adapter files, the task hashes and the upstream commit (`pilot.py:96-100`), not the whole kernel.

So the code-hash binding was enforced by a separate identity check and a recorded rebind, and is not carried by the approval record. Follow-up: add `code_hash` to `ApprovalRecord` (issue #42) so the approval itself binds it, as the pre-registration requires.
