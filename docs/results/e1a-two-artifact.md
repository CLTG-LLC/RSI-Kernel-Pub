## Limitation (S5 addendum §2, quoted)

The addendum's §2 limitation is stated here as a limitation, not as a result:

> **Limitation: live D4 is add/discard only**
>
> The unchanged kernel passes the same original champion to every proposal inside one campaign (`loop.py:run_campaign` -> `proposer(champion, ...)`). With an empty seed, every live D4 call therefore offers only `add` and `discard`: `merge` and `revise` require an existing registered entry, and only the selected candidate — not the champion — could carry one. Consequences, stated up front:
>
> - the S5 run yields **no merge/revise claim** and **no cumulative-growth claim** (one admitted entry per attempt, from an empty library);
> - `merge`/`revise` remain covered by the adapter's write-guard tests only.

The `{add, discard}` criterion set recorded in all nine D4 envelopes is that limitation showing up in the data. Nothing in this report tests `merge` or `revise`; the zero admitted entries also mean the run cannot speak to library growth in either direction.

## Conditional prediction (S5 addendum §9.2)

The observed all-discard outcome is consistent with the hypothesis, not confirmation of it. All four prerequisites held for group 003; groups 001 and 002 did not satisfy the successful-response prerequisite because each had one operational fallback.

- The other three prerequisites held in every group: the champion's nine dev observations are valid and complete; D2 answered `c1` on all three attempts; and three valid drafts reached D4.
- The fourth prerequisite ("every live D4 response succeeds") failed in groups 001 and 002: one `malformed` and one `timeout` fell back. The two fallbacks still discarded, but as operational outcomes, not as Jev choices.
- The champions' dev pass counts (1/9, 3/9, 4/9) sit at or below the probe states that returned discard in §9.1. That is consistent with the hypothesis; it is not a threshold, was not used as one, and does not establish why the model discarded.
- The D4 state cannot see the draft (§9.4 below), so "the model discarded the entry" and "the model discarded on the champion's dev record" are not distinguishable from this data.

## How this run is reported (S5 addendum §9.3, quoted)

> Jev matched the recorded discard baseline on every successful D4 response; no improvement was demonstrated, and paired efficacy comparisons are unavailable.

## Limitation (S5 addendum §9.4)

> The kernel is frozen for #6, and its D4 envelope carries the champion's state only (`loop.py:143–198`; `docs/design.md:33–55`). The D4 request therefore describes **the champion, not the proposed entry**, so a D4 `discard` is a statement about the champion's dev record as much as about the draft. Adding post-evaluation or entry-level metrics to admission would change the registered flow, so it is **not applied in S5**; the remedy is deferred to a later kernel slice. S5 runs as pre-registered (option a: run it and disclose the limit).

The nine recorded D4 states bear this out: each carries only `c1.dev_pass_count` / `c1.dev_fail_count` and says nothing about the draft. No entry text enters the envelope or the decision log, on the addendum's canary-test guarantee (§5).

Agreement with the baseline is therefore **not** evidence that the proposed entries were bad. The entries were never evaluated: D4 is admission, not a quality judgement (§3).
